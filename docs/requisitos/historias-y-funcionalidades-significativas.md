# Historias de usuario y funcionalidades significativas

> Fuente: FuncionalidadesSignificativas.xlsx.


## Hoja: HU

| Nombre Historia de Usuario | Card |
|---|---|
| HU01. Inicio de sesión | Como Administrador o Cajero, quiero iniciar sesión mediante un usuario y contraseña registrados en el sistema, para acceder únicamente a las funcionalidades correspondientes a mi rol. |
| HU02. Gestión de usuarios | Como Administrador, quiero crear, consultar, modificar y eliminar usuarios del sistema, para mantener controladas las cuentas de las personas autorizadas a utilizar la plataforma. |
| HU03. Gestión de empleados | Como Administrador, quiero registrar y actualizar la información de los empleados de la cafetería, para mantener organizada y actualizada la información del personal que trabaja en el establecimiento. |
| HU04. Gestión de productos | Como Administrador, quiero registrar, consultar, modificar y eliminar los productos ofrecidos por la cafetería, para mantener actualizado el catálogo de productos disponibles para la venta. |
| HU05. Consulta de productos para la venta | Como Cajero, quiero consultar los productos disponibles junto con sus precios y estado de disponibilidad, para seleccionar correctamente los productos solicitados por los clientes al momento de registrar una venta. |
| HU06. Registro de ventas | Como Cajero, quiero registrar una venta seleccionando los productos, cantidades y valores correspondientes, para llevar un control preciso de las transacciones realizadas en la cafetería. |
| HU07. Modificación de una venta antes de confirmarla | Como Cajero, quiero modificar los productos y cantidades de una venta antes de confirmarla, para corregir errores en el pedido del cliente antes de almacenarlo definitivamente. |
| HU08. Consulta de ventas | Como Administrador, quiero consultar las ventas realizadas en la cafetería, para revisar las transacciones registradas y realizar seguimiento a la operación del negocio. |
| HU09. Filtrado de ventas por periodo | Como Administrador, quiero consultar las ventas filtrándolas por un periodo de tiempo determinado, para analizar las transacciones realizadas durante fechas específicas. |
| HU10. Generación de reportes de ventas | Como Administrador, quiero generar reportes de las ventas realizadas durante un periodo determinado, para analizar el comportamiento de las ventas y apoyar la toma de decisiones de la cafetería. |
| HU11. Consulta de productos más vendidos | Como Administrador, quiero consultar los productos con mayor cantidad de ventas durante un periodo determinado, para identificar cuáles productos tienen mayor demanda en la cafetería. |
| HU12. Control de disponibilidad de productos | Como Administrador, quiero actualizar el estado de disponibilidad de los productos, para evitar que el Cajero registre ventas de productos que no pueden ser ofrecidos a los clientes. |
| HU13. Cierre de sesión | Como Administrador o Cajero, quiero cerrar mi sesión en el sistema, para impedir que otra persona pueda utilizar mi cuenta cuando termine de utilizar la plataforma. |

## Hoja: FuncionalidadesSignificativas

| Identificador Requisito Funcional/Historia de Usuario/Caso de Uso | Especificación Requisito Funcional/Historia de Usuario/Caso de Uso | Tipo de funcionalidad significativa | Justificación | Observación |
|---|---|---|---|---|
| RF1 | El sistema debe permitir al administrador registrarse con: nombre, apellido, nombre de usuario y contraseña. | Valor de negocio | Es el primer paso obligatorio para que exista un administrador en el sistema, sin lo cual no hay dueño de la información; combina valor de negocio, porque el administrador necesita una identidad propia para operar su cafetería, con reto técnico, ya que implica validar datos, prevenir duplicados y manejar el proceso de creación de cuenta de forma segura. | Este registro se realiza una vez durante la configuración inicial. Por seguridad, la contraseña debe cumplir con un estándar mínimo de complejidad (letras y números) y el nombre de usuario debe ser único en la plataforma. |
| RF3 | El sistema debe permitir al administrador registrar a un cajero con: nombre, apellido, nombre de usuario, rol y contraseña. | Valor de negocio | Habilita el trabajo en equipo dentro de la cafetería, permitiendo delegar el registro de ventas en un empleado en lugar de que el administrador opere todo solo — es principalmente valor de negocio, con una complejidad técnica baja al ser un registro estándar. | Cada cajero contará con sus propias credenciales de acceso para garantizar la responsabilidad e identificación en los cierres de caja y cobros realizados. El usuario administrador será quien controle el alta, baja o modificación de las cuentas de cajeros. |
| RF5 | El sistema debe permitir a los usuarios acceder con nombre de usuario y contraseña. | Valor de negocio | Es la acción más repetida del sistema, ya que cada persona debe iniciar sesión cada vez que lo usa; es valor de negocio porque sin acceso no hay uso del producto, y reto técnico porque debe manejarse de forma segura mediante sesiones y control de expiración. | El sistema mantendrá la sesión activa de forma segura e iniciará automáticamente en la pantalla asignada según el perfil del usuario (por ejemplo, el módulo de ventas para el cajero o el panel de control para el administrador). Se incluirá la opción de "Cerrar sesión" para proteger el acceso. |
| RF6 | El sistema debe validar que las credenciales de inicio de sesión sean correctas. | Reto técnico | Previene accesos indebidos y protege la información financiera sensible de cada cafetería; es un reto técnico ante todo, ya que es una validación interna, invisible para el usuario cuando funciona bien, pero crítica desde el punto de vista de seguridad. | Las contraseñas se almacenarán y compararán mediante algoritmos de encriptación seguros (nunca en texto plano). Si las credenciales no coinciden, el sistema mostrará un mensaje genérico de error de acceso por motivos de seguridad. |
| RF7 | El sistema debe asociar cada usuario (administrador o cajero) a una o varias cafeterías, con un rol en cada una (actualizado por ADR-0016). | Reto técnico | Es la base que permite que el sistema sirva a múltiples negocios sin mezclar su información; es un reto técnico principalmente, una decisión de modelo de datos que el usuario no percibe directamente, pero sin la cual el sistema no podría operar como producto multi-cliente. | En cada petición el usuario actúa en una sola cafetería, la que eligió (encabezado `X-Cafeteria-Id`), y solo si tiene una membresía activa en ella; su rol es el de esa membresía. Las consultas y transacciones se filtran automáticamente por esa cafetería (RLS). |
| RF8 | El sistema debe garantizar que el administrador solo pueda consultar y gestionar la información de su propia cafetería. | Ambos | Protege la confidencialidad del negocio y es lo que hace confiable ofrecer el sistema a distintas cafeterías, incluso competidoras entre sí; combina reto técnico, porque requiere control de acceso a nivel de datos, con valor de negocio directo, ya que la confianza del cliente depende de que sus datos estén realmente aislados. | Este aislamiento se aplica a nivel de base de datos para todas las consultas y reportes. Ningún usuario, independientemente de su nivel de acceso local, podrá ver registros de otra sucursal a menos que cuente con un perfil de Superadministrador global. |
| RF9 | El sistema debe garantizar que el cajero solo pueda registrar y consultar movimientos de la cafetería a la que pertenece. | Ambos | Extiende esa misma protección al cajero, evitando fugas de información entre negocios distintos; combina reto técnico y valor de negocio por las mismas razones que RF8, aplicadas al segundo rol. | Los permisos del cajero estarán limitados a su turno y a su local asignado. Cualquier acción que requiera privilegios elevados (como anulaciones, descuentos especiales o cierres fuera de norma) solicitará la autorización o clave de confirmación del administrador. |
| RF14 | El sistema debe permitir al administrador registrar egresos de la cafetería. | Valor de negocio | Cubre una de las dos mitades de la información financiera básica del negocio (junto con los ingresos); es principalmente valor de negocio, al ser una necesidad operativa directa del administrador sin mayor complejidad técnica. | Cada gasto registrado requerirá un monto, concepto/categoría y la identificación del usuario que lo ingresó. Se recomienda exigir el número de comprobante o factura asociada para respaldar la auditoría y el reporte final de egresos. |
| RF17 | El sistema debe mostrar al administrador el total de ingresos y egresos. | Valor de negocio | Es el primer resumen entendible que recibe el administrador a partir de sus datos, respondiendo directamente "¿cuánto entró y cuánto salió?"; es principalmente valor de negocio, sin mayor complejidad técnica asociada. | La vista incluirá indicadores visuales inmediatos (total vendido, total gastado y balance neto resultante). Permitirá filtrar los resultados por día, semana, mes o rangos de fecha personalizados para facilitar las comparaciones financieras. |
| RF18 | El sistema debe permitir al administrador crear, editar y eliminar categorías de ingresos y egresos. | Valor de negocio | Permite organizar y clasificar los movimientos financieros de acuerdo con las necesidades de la cafetería. | El sistema permitirá crear, editar o eliminar categorías y subcategorías personalizadas. Al registrar un ingreso o gasto, la asignación de una categoría será un campo obligatorio para mantener la consistencia de los reportes. |
| RF19 | El sistema debe permitir al administrador configurar umbrales de alerta (porcentaje de variación y tipo de comparación: semana/mes/año). | Ambos | Le da al administrador control sobre qué tan sensible quiere que sea el sistema frente a variaciones de su negocio, es principalmente valor de negocio diferencial. | Los umbrales configurados se guardarán en las preferencias del sistema por cafetería. La lógica de negocio evaluará periódicamente los egresos e ingresos frente a estos parámetros, activando indicadores visuales o alertas automáticas en el módulo de reportes cuando se supere o no se alcance un límite establecido. |
| RF22 | El sistema debe permitir al administrador crear, editar y eliminar productos del menú, incluyendo su precio. | Valor de negocio | Sin catálogo de productos, el cajero no tendría de dónde seleccionar qué se vendió,  es valor de negocio, personalización directa del negocio con complejidad técnica baja-media. | Toda actualización de precios afectará inmediatamente a las nuevas ventas registradas, sin modificar el historial ni los montos de ventas cobradas previamente. El sistema permitirá gestionar el estado de disponibilidad del producto (ej. disponible / agotado) para no ofrecer ítems fuera de stock. |
| RF23 | El sistema debe permitir al administrador marcar un producto como "producto base" o "adición". | Reto técnico | Habilita la posibilidad de vender combinaciones reales (producto más extras), acercando el sistema a cómo opera una cafetería de verdad; es principalmente un reto técnico, al requerir un modelo de datos más elaborado que un catálogo plano. | Las adiciones podrán vincularse a uno o varios productos base y tendrán su propio costo o precio incremental. El sistema permitirá configurar si una adición es opcional u obligatoria según la categoría del producto, reflejándose de manera clara en la comanda y en el ticket de venta. |
| RF24 | El sistema debe permitir al cajero seleccionar un producto base del menú al registrar una venta. | Valor de negocio | Conecta cada venta con algo concreto que se vendió, en vez de un monto libre sin contexto, permitiendo luego analizar qué productos generan más ingresos; combina valor de negocio, por la mejor trazabilidad de las ventas, con reto técnico, al requerir relacionar movimientos con el catálogo de productos. | La interfaz presentará los productos ordenados por categorías o accesos directos para facilitar una selección rápida. La elección del producto principal habilitará, si corresponde, la pantalla o ventana emergente para incluir adiciones, modificaciones de tamaño o notas especiales de preparación. |
| RF25 | El sistema debe permitir al cajero agregar una o más adiciones a un producto base al registrar una venta. | Valor de negocio | Refleja la forma real en que se vende en una cafetería (ej. "café con leche de almendra"), dando más precisión a los datos; es principalmente un reto técnico, ya que exige un modelo de datos más complejo que un simple registro de venta. | Al elegir un producto base en la pantalla de cobro, el sistema desplegará automáticamente las adiciones compatibles configuradas previa y exclusivamente para esa categoría. Cada complemento seleccionado ajustará el valor total de la orden y se reflejará detalladamente en el ticket o comanda enviada a preparación. |
| RF26 | El sistema debe calcular automáticamente el valor total de la venta sumando el precio del producto base más el de sus adiciones. | Ambos | Evita errores de cálculo manual del cajero, especialmente en horas de alta rotación; es un reto técnico, pues implica lógica de negocio no trivial para sumar correctamente producto base y adiciones. | El motor de cálculo actualizará el subtotal y total a pagar en tiempo real ante cualquier cambio en el carrito de compra (agregar, eliminar o modificar unidades/adiciones). La lógica considerará las reglas de impuestos, descuentos globales o por ítem si estuvieran habilitados. |
| RF27 | El sistema debe registrar el detalle de cada venta (producto base y adiciones incluidas). | Reto técnico | Permite analizar después qué se vendió exactamente, no solo un total genérico, enriqueciendo los reportes futuros; es un reto técnico, ya que implica persistir información estructurada más compleja que un simple monto. | Cada registro de venta quedará vinculado al cajero que la ejecutó, la fecha, hora e identificador único de ticket. Los datos del detalle histórico serán inmutables para resguardar la integridad contable y servirán de base para el cálculo de consumo de insumos y reportes de productos más vendidos. |
| RF31 | El sistema debe mostrar al administrador un dashboard con las métricas del período seleccionado (día/semana/mes/año) al momento de la consulta. | Ambos | Es la pantalla principal que concentra visualmente el valor de todas las demás funcionalidades del sistema, siendo la experiencia central de uso diario del administrador; es valor de negocio, con complejidad técnica moderada en las consultas agregadas que lo alimentan. | El sistema ejecutará consultas agrupadas sobre los registros de ingresos, egresos y ventas finalizadas para generar indicadores clave (KPIs como total vendido, ticket promedio o margen neto). Las métricas se actualizarán dinámicamente cada vez que el usuario modifique el filtro de fechas o la cafetería seleccionada. |
| RF32 | El sistema debe permitir al administrador seleccionar el período a visualizar en el dashboard. | Valor de negocio | Entrega la visión periódica que el administrador necesita para evaluar su negocio en distintas escalas de tiempo; es valor de negocio, una expectativa básica de cualquier sistema financiero, con complejidad técnica moderada en la agregación de datos. | La interfaz incluirá controles tipo selector de fechas (date picker) con opciones predefinidas (Ej.: "Hoy", "Esta semana", "Mes actual", "Mes anterior") y la posibilidad de definir un rango personalizado de fecha inicio y fecha fin. El valor seleccionado recalculará de forma automática las tablas, gráficos y KPIs presentes en la vista de reportes. |
| RF33 | El sistema debe generar reportes financieros (semanal, mensual, anual). | Ambos | Entrega la visión periódica que el administrador necesita para evaluar su negocio en distintas escalas de tiempo; es valor de negocio, una expectativa básica de cualquier sistema financiero, con complejidad técnica moderada en la agregación de datos. | El motor de reportes agrupará las transacciones procesadas (ventas, adiciones y gastos) según el rango de fechas seleccionado, generando resúmenes estructurados en tablas o estados financieros consolidados. Los datos procesados podrán ser exportables o visualizables en pantalla de forma inmediata sin alterar los registros contables de origen. |
| RF34 | El sistema debe calcular automáticamente las ganancias (utilidad neta) de la cafetería. | Ambos | Responde la pregunta más importante para cualquier dueño de negocio, "¿estoy ganando o perdiendo?"; combina valor de negocio evidente con reto técnico, ya que el cálculo debe ser exacto y consistente cada vez que se genera. | La utilidad neta se calculará automáticamente a partir de los ingresos y egresos registrados en el período seleccionado. El sistema deberá mostrar el resultado de forma clara para facilitar el análisis financiero de la cafetería. |
| RF36 | El sistema debe comparar automáticamente el período actual contra el período anterior según la configuración del administrad | Ambos | Convierte un reporte estático en información con contexto histórico, permitiendo detectar tendencias, y es uno de los pilares que distingue al producto frente a una competencia que solo muestra reportes históricos aislados; es principalmente valor de negocio diferencial. | La comparación se realizará entre el período seleccionado y el período anterior equivalente, utilizando la configuración definida por el administrador. El sistema deberá mostrar la variación obtenida de forma comprensible. |
| RF37 | El sistema debe generar alertas automáticas cuando una variación supere el umbral configurado. | Ambos | Es la acción concreta que cumple la promesa central del proyecto de avisar antes de que el problema sea grave; combina valor de negocio, al cumplir la promesa del pitch, con reto técnico, al requerir lógica de comparación y disparo automático de eventos. | Las alertas se generarán automáticamente cuando la variación calculada supere el porcentaje establecido por el administrador. Cada alerta deberá indicar el período, el tipo de variación y el valor correspondiente. |
| RF39 | El sistema debe encriptar las contraseñas de los usuarios. | Reto técnico | Protege la información de acceso ante cualquier filtración de la base de datos, algo crítico en un sistema que maneja datos financieros; es un reto técnico puro, invisible para el usuario cuando funciona correctamente. | Las contraseñas no deberán almacenarse directamente en la base de datos. El sistema deberá utilizar un mecanismo de protección adecuado para evitar que las credenciales puedan ser consultadas en texto plano. |
| RF40 | El sistema debe restringir el acceso a funcionalidades según el rol del usuario. | Ambos | Evita que un cajero realice acciones exclusivas del administrador (o viceversa), protegiendo la integridad del negocio; es un reto técnico, ya que requiere lógica de control de acceso aplicada de forma consistente en todo el sistema. | Las funcionalidades disponibles dependerán del rol del usuario autenticado. El administrador tendrá acceso a las funciones de gestión y configuración, mientras que el cajero tendrá acceso únicamente a las operaciones permitidas para su rol. |
| RF54 | Generar recomendaciones mediante IA a partir de los reportes financieros | Ambos | Es el diferenciador más fuerte del proyecto, ya que ningún competidor directo ofrece hoy un análisis automático explicativo; combina valor de negocio, al responder directamente a la motivación del proyecto con un reto técnico considerable, al requerir integración con modelos de IA y procesamiento de datos financieros. | El módulo procesará los datos consolidados de ventas, adiciones y costos para generar un panel de observaciones o sugerencias accionables (por ejemplo, detectar caídas de ventas en ciertas horas, recomendar combos de productos o alertar sobre alza en costos de insumos). El usuario administrador podrá consultar estas recomendaciones al revisar sus reportes periódicos. |
| RF55 | Presentar las recomendaciones en lenguaje natural | Ambos | Hace que la información sea comprensible para un administrador sin formación técnica ni contable, cumpliendo la promesa de simplicidad del producto; combina valor de negocio, por la accesibilidad de la información, con reto técnico, al requerir generación de lenguaje natural coherente y útil. | La interfaz convertirá los resultados de los algoritmos en oraciones redactadas de forma sencilla, descriptiva y contextualizada para el sector gastronómico (por ejemplo: "Se observa un incremento del 15% en las ventas de espresso los viernes por la tarde; considera crear una promoción de repostería para acompañarlo"). |
| RF57 | Notificar alertas en tiempo real generadas por la IA | Ambos | Cumple con avisarle al administrador sobre algun problema "antes de que la pérdida sea grande", no al cierre del mes; combina valor de negocio, al ser la promesa central del producto, con reto técnico, al requerir infraestructura de notificaciones en tiempo real. | El sistema emitirá avisos instantáneos (vía notificaciones push en la plataforma, banners en la interfaz o mensajes) cada vez que el modelo de IA detecte un patrón fuera de lo normal durante la operación diaria. El administrador podrá configurar o marcar como atendidas dichas alertas dentro del panel de control. |
