# ADR-0017: Usar Google Cloud API Gateway como puerta de entrada al backend

## Estado
Aceptado. Pendiente de montar en la nube. Complementa ADR-0001 (autenticación con Firebase), ADR-0013 (Google Cloud) y ADR-0014 (vault de secretos). El profesor pidió que el API Gateway aparezca en el modelo C4 desde el nivel 1.

## Criterios de evaluación
**Resumen:** Se buscaba una única entrada pública para el backend, que rechace peticiones sin un token válido antes de que lleguen a Cloud Run y que no agregue código ni servidores que el equipo tenga que mantener.

**Detalles:**
- Una sola URL pública; el backend no se puede llamar directamente desde internet.
- Validar el token de Firebase en la entrada, sin quitarle al backend su propia verificación.
- Misma nube y misma facturación que el resto (ADR-0013).
- Bajo costo y poca operación, por el tamaño del equipo.
- Que deje pasar los encabezados propios (`X-Cafeteria-Id`, `Idempotency-Key`) y el preflight de CORS.

## Candidatos a considerar
**Candidatos:**
- Google Cloud API Gateway.
- Spring Cloud Gateway desplegado como un segundo servicio en Cloud Run.
- Exponer Cloud Run directamente, sin gateway.
- Reescrituras de Firebase Hosting hacia Cloud Run.

## Investigación y análisis de cada candidato

### Cumple/no cumple con los criterios y por qué
- **Google Cloud API Gateway:** Cumple — servicio administrado que se configura con un archivo OpenAPI, valida tokens de Firebase y llama a Cloud Run con su propia cuenta de servicio, así Cloud Run puede quedar privado.
- **Spring Cloud Gateway:** Cumple a medias — hace todo lo necesario, pero es otra aplicación para programar, desplegar, actualizar y pagar.
- **Cloud Run directo:** No cumple — el backend queda expuesto y no hay una capa antes de él.
- **Firebase Hosting con reescrituras:** No cumple — sirve para enrutar, pero no valida tokens ni permite dejar Cloud Run privado.

### Análisis de costos

**Google Cloud API Gateway:**
- Licencias: los primeros 2 millones de llamadas al mes son gratis; el volumen esperado está muy por debajo.
- Capacitación: baja, se escribe un archivo OpenAPI 2.0.
- Operación: casi ninguna, Google administra el servicio.
- Medición: un archivo nuevo en el repo (`infra/api-gateway/openapi.yaml`) y un cambio pequeño en `FirebaseAuthFilter`.

**Spring Cloud Gateway:**
- Licencias: no aplica, pero es otra instancia de Cloud Run con su costo.
- Capacitación: media.
- Operación: un segundo servicio con su propio CI, imagen y actualizaciones.
- Medición: un proyecto nuevo.

**Cloud Run directo:**
- Licencias: ninguna.
- Capacitación: ninguna.
- Operación: ninguna extra.
- Medición: no hay forma de cerrar el backend.

**Firebase Hosting con reescrituras:**
- Licencias: incluido en el plan de Firebase.
- Capacitación: baja.
- Operación: baja.
- Medición: no resuelve la validación de tokens.

### Análisis FODA

**Google Cloud API Gateway:**
- Fortalezas: administrado, barato, valida tokens de Firebase y deja Cloud Run privado.
- Debilidades: solo acepta OpenAPI 2.0; cada ruta nueva hay que agregarla al archivo.
- Oportunidades: más adelante se pueden agregar cuotas o claves de API por cliente.
- Amenazas: si el archivo OpenAPI queda desactualizado, una ruta nueva no se puede usar desde afuera.

**Spring Cloud Gateway:**
- Fortalezas: flexible y en el mismo lenguaje del backend.
- Debilidades: más código y más despliegues.
- Oportunidades: filtros personalizados.
- Amenazas: un servicio más que se puede caer o quedar sin actualizar.

**Cloud Run directo:**
- Fortalezas: lo más simple.
- Debilidades: sin capa de entrada.
- Oportunidades: ninguna.
- Amenazas: cualquiera puede llamar al backend y gastar recursos con peticiones inválidas.

**Firebase Hosting con reescrituras:**
- Fortalezas: sirve el frontend y el backend bajo el mismo dominio.
- Debilidades: no valida nada.
- Oportunidades: se puede usar para el frontend.
- Amenazas: da una falsa sensación de que hay un gateway.

### Opiniones y comentarios internos
**Resumen:** El profesor pidió el API Gateway en el C4 y el equipo quiere que el backend no quede expuesto. Se elige la opción que no agrega código para mantener.

- Del equipo: el backend sigue verificando el token y la membresía aunque el gateway ya lo haya hecho. No se confía solo en el gateway.

### Opiniones y comentarios externos
Documentación de Google Cloud API Gateway sobre autenticación con Firebase y sobre las extensiones de OpenAPI.

### Anécdotas
Ninguna registrada aún.

## Recomendación
**Resumen:** Poner Google Cloud API Gateway delante de Cloud Run. El gateway valida el token de Firebase y es el único que puede invocar el backend.

**Detalles:**
- Archivo `infra/api-gateway/openapi.yaml` (OpenAPI 2.0) con todas las rutas bajo `/api`: `acceso`, `ingresos`, `ingresos/libres`, `ingresos/catalogo`, `ingresos/{idVenta}/deshacer`, `egresos` y `movimientos`.
- Validación del token de Firebase en el OpenAPI: emisor `https://securetoken.google.com/jjskafee`, audiencia `jjskafee`.
- `x-google-backend` con la URL de Cloud Run y `path_translation: APPEND_PATH_TO_ADDRESS`.
- Las operaciones `OPTIONS` van sin seguridad, para que el preflight de CORS llegue al backend.
- Cloud Run queda privado: solo la cuenta de servicio del gateway tiene `roles/run.invoker`.
- Cuando el gateway llama a un Cloud Run privado, pone su propio token en `Authorization` y copia el original a `X-Forwarded-Authorization`. `FirebaseAuthFilter` usa `X-Forwarded-Authorization` si viene y, si no, `Authorization` (como en local).
- En el perfil `gcp` el backend usa `server.servlet.context-path=/api`. En local sigue sin prefijo.
- Revisar esta decisión si se necesitan reglas de enrutamiento que el API Gateway no soporte, o si el sistema pasa a varios servicios.
