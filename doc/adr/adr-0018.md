# ADR-0018: Usar Google Cloud Armor (WAF) con un balanceador de carga delante del API Gateway

## Estado
Aceptado. Pendiente de montar en la nube. Complementa ADR-0017 (API Gateway) sin reemplazarlo: el gateway sigue validando el token de Firebase, pero ahora queda detrás de un balanceador con Cloud Armor. También se apoya en ADR-0013 (Google Cloud) y ADR-0014 (Secret Manager).

El WAF no se contempló en el diseño inicial porque la prioridad fue el aislamiento entre cafeterías (RLS) y la autenticación. Se identificó como faltante al revisar la Línea Base Técnica de la guía de evaluación, después de entregar la documentación, y se agrega ahora.

## Criterios de evaluación
**Resumen:** Se buscaba un WAF que frene ataques comunes (OWASP) y abusos de tráfico antes de que lleguen al API Gateway y a Cloud Run, sin código propio para mantener y sin poder saltárselo.

**Detalles:**
- Cumplir la Línea Base Técnica de la guía de evaluación, que pide un WAF.
- Reglas administradas contra los ataques del OWASP Top 10 (inyección SQL, XSS, inclusión de archivos, ejecución remota, escáneres).
- Límite de peticiones por IP.
- Misma nube y misma facturación que el resto (ADR-0013).
- Bajo costo y poca operación, por el tamaño del equipo. Que se pueda quitar fácil después de la evaluación.
- Que no se pueda saltar entrando por otra URL.
- Funcionar sin dominio propio por ahora.

## Candidatos a considerar
**Candidatos:**
- Google Cloud Armor con un balanceador de carga HTTPS externo global.
- Cloudflare WAF.
- Sin WAF, confiando en el API Gateway y el backend.
- Un filtro dentro de la aplicación.

## Investigación y análisis de cada candidato

### Cumple/no cumple con los criterios y por qué
- **Cloud Armor con balanceador:** Cumple — servicio administrado de Google con reglas OWASP preconfiguradas y límite por IP. Se conecta al API Gateway con una serverless NEG y puede agregar un encabezado secreto a cada petición para que el backend rechace lo que no pasó por el WAF.
- **Cloudflare WAF:** Cumple a medias — es un buen WAF, pero exige un dominio propio administrado en Cloudflare (hoy no hay) y es otro proveedor con otra facturación.
- **Sin WAF:** No cumple — el gateway valida el token y el backend valida todo, pero no hay una capa que frene ataques conocidos ni abusos de tráfico, y la guía pide WAF.
- **Filtro dentro de la aplicación:** No cumple — no es un WAF real: el tráfico malicioso ya llegó a Cloud Run y gasta recursos, y las reglas las tendría que escribir y mantener el equipo.

### Análisis de costos

**Cloud Armor con balanceador:**
- Licencias: balanceador cerca de USD 18/mes (regla de reenvío); política de Cloud Armor USD 5/mes; cerca de USD 1/mes por regla (8 reglas: 6 OWASP, el límite por IP y la regla por defecto); USD 0,75 por millón de peticiones. Total aproximado: unos USD 31/mes más las peticiones, que con el volumen esperado son centavos. Una IP reservada sin usar también se cobra.
- Capacitación: baja, se configura con comandos de `gcloud`.
- Operación: baja; revisar los registros al activar las reglas y borrar todo con un script después de la evaluación.
- Medición: dos scripts (`infra/waf/crear-waf.ps1` y `eliminar-waf.ps1`) y un filtro pequeño en el backend (`OrigenWafFilter`).

**Cloudflare WAF:**
- Licencias: las reglas OWASP administradas están en los planes pagos (desde unos USD 20/mes) más el dominio propio (unos USD 10/año).
- Capacitación: media, es otra consola y otra forma de configurar.
- Operación: media; DNS, certificados y reglas en otro proveedor.
- Medición: mover el DNS de un dominio a Cloudflare y configurar el encabezado secreto allá.

**Sin WAF:**
- Licencias: ninguna.
- Capacitación: ninguna.
- Operación: ninguna extra.
- Medición: no cumple la guía.

**Filtro dentro de la aplicación:**
- Licencias: ninguna.
- Capacitación: alta para escribir reglas que sirvan de verdad.
- Operación: alta; mantener las reglas al día con ataques nuevos.
- Medición: código propio de seguridad, difícil de probar bien.

### Análisis FODA

**Cloud Armor con balanceador:**
- Fortalezas: administrado, en la misma nube, reglas OWASP mantenidas por Google, límite por IP y registro de cada decisión en Cloud Logging.
- Debilidades: la conexión del balanceador con el API Gateway (serverless NEG para API Gateway) está en Preview; el valor del encabezado secreto lo puede ver quien tenga acceso a la configuración del balanceador en el proyecto.
- Oportunidades: más reglas (por país, por bots) y protección contra DDoS si el producto crece; pasar a un dominio propio sin cambiar el diseño.
- Amenazas: la URL `*.gateway.dev` del API Gateway no se puede apagar y sigue abierta (mitigado: el balanceador agrega `X-JJSKaffee-Origen` con un valor secreto y el backend responde 403 a lo que no lo traiga); falsos positivos que bloqueen ventas legítimas (mitigado: las reglas empiezan en modo preview, que solo registra, y con sensibilidad 1, la más baja); `sslip.io` es un servicio gratuito de terceros y no un dominio propio, sin garantía de disponibilidad.

**Cloudflare WAF:**
- Fortalezas: WAF y CDN muy usados, con plan gratuito para lo básico.
- Debilidades: exige dominio propio en Cloudflare; otro proveedor fuera de Google Cloud.
- Oportunidades: servir también el frontend con su CDN.
- Amenazas: la URL `*.gateway.dev` también quedaría abierta y habría que resolverla igual.

**Sin WAF:**
- Fortalezas: lo más simple y sin costo.
- Debilidades: no frena ataques conocidos ni abusos antes de llegar al gateway.
- Oportunidades: ninguna.
- Amenazas: no cumple la Línea Base Técnica; un abuso de tráfico gasta recursos de Cloud Run y Cloud SQL.

**Filtro dentro de la aplicación:**
- Fortalezas: sin costo extra y en el mismo lenguaje.
- Debilidades: no es un WAF; corre después de que la petición ya llegó.
- Oportunidades: ninguna que no cubra mejor un WAF administrado.
- Amenazas: falsa sensación de protección.

### Opiniones y comentarios internos
**Resumen:** El equipo reconoce que el WAF no estaba en el diseño inicial porque la prioridad fue el aislamiento entre cafeterías y la autenticación. Al revisar la Línea Base Técnica de la guía de evaluación se vio que faltaba, y se eligió la opción que queda en la misma nube y no agrega código para mantener.

- Del equipo: el WAF es una capa más, no reemplaza nada. El API Gateway sigue validando el token y el backend sigue verificando token, membresía, permisos y datos (consultas parametrizadas y validaciones). No se confía solo en el WAF.
- Del equipo: como el WAF se monta para la evaluación, debe poder borrarse con un solo script para no seguir pagando.

### Opiniones y comentarios externos
Documentación de Google Cloud Armor sobre reglas WAF preconfiguradas (OWASP ModSecurity CRS, versión v33), límite de peticiones y modo preview; documentación de API Gateway sobre el uso de un balanceador de carga con serverless NEG (Preview); documentación de `sslip.io`.

### Anécdotas
Al diseñar el balanceador se vio que la URL `*.gateway.dev` del API Gateway no se puede apagar, así que alguien podría llamar al gateway directamente y saltarse el WAF. Por eso se agregó el encabezado secreto `X-JJSKaffee-Origen`.

## Recomendación
**Resumen:** Poner un balanceador de carga HTTPS externo global con Cloud Armor delante del API Gateway. El backend rechaza toda petición que no traiga el encabezado secreto que pone el balanceador.

**Detalles:**
- Recorrido: Navegador → Balanceador HTTPS + Cloud Armor → API Gateway (serverless NEG) → Cloud Run privado → Cloud SQL.
- Sin dominio propio por ahora: IP estática global y el dominio gratuito `<ip-con-guiones>.sslip.io` con certificado administrado por Google. El frontend usa `VITE_API_URL=https://<ip-con-guiones>.sslip.io/api`.
- Reglas OWASP preconfiguradas con sensibilidad 1, acción `deny(403)`: `sqli-v33-stable`, `xss-v33-stable`, `lfi-v33-stable`, `rce-v33-stable`, `scannerdetection-v33-stable` y `protocolattack-v33-stable`.
- Límite por IP: 100 peticiones cada 60 segundos; el exceso recibe `deny(429)`. Regla por defecto: permitir.
- Todas las reglas empiezan en modo preview (solo registran). Se activan después de revisar en Cloud Logging qué habrían bloqueado.
- El balanceador agrega `X-JJSKaffee-Origen` con un valor secreto guardado en Secret Manager (`jjskaffee-waf-secreto`). `OrigenWafFilter` lo exige antes de revisar el token, incluido el preflight (`OPTIONS`), lo compara en tiempo constante y responde 403 con un mensaje genérico. En local y en pruebas el secreto está vacío y el filtro no hace nada.
- Scripts: `infra/waf/crear-waf.ps1` y `infra/waf/eliminar-waf.ps1`. Guía: `docs/despliegue/waf.md`.
- Revisar esta decisión si se compra un dominio propio, si la conexión del balanceador con API Gateway cambia al salir de Preview, o si el costo deja de justificarse después de la evaluación.
